### 4.4 Design decisions

**No silent data loss.** The loader reports every value that fails to parse. After the identifier fix the count is zero: a value becomes null only if it was blank, missing, or the declared `WIP` sentinel. A test compares null counts column by column against the raw CSVs, so loss cannot creep back in.

**Identifiers are text, not numbers.** Building the loader exposed two problems with treating `Owner.Comm.Postal.Code` as numeric: it silently discarded two foreign postal codes (DQ-012), and it would strip leading zeros. The same reasoning applies to `AppID`, `ClientID`, `SALES_ID`, `Branch_No`, `Claim_No` and `Inforce.month` — none is a quantity, and typing them as numbers would let joins depend on floating-point equality and permit meaningless arithmetic such as an average AppID. All twelve are now typed as identifiers and held as text (DQ-013). `Table.num()` refuses them with a message pointing at the right accessor.

**The DQ-001 repair is opt-in.** By default the corrupted `AppID` is left alone and surfaces as exactly one orphan in each affected join. Passing `repair_corrupted_appid=True` applies the fix and records it in the `LoadReport` with the evidence that justified it, so a repaired load can always be told apart from a clean one.

**Every operation is auditable.** Each query step records its operation, its detail and its row counts in and out. Row counts must be continuous across a chain, which a test asserts. Joins additionally record key coverage, unmatched keys and maximum fan-out, so a join that would multiply rows is visible rather than silently inflating every downstream total.

### 5.4 Design decisions

**Formulas and rules are separated deliberately.** A formula is arithmetic: it has one correct answer given its inputs. A business rule is a judgement about *which rows count* — which population, which threshold, which exclusion. Executives can and should challenge the second kind, so every rule carries its statement, its rationale, and the data-quality finding that motivated it.

**Three semantics are explicit for every formula**, because they are where calculations quietly go wrong:

| Concern | Rule applied |
|---|---|
| Null handling | `F-AVG` divides by present values, never by row count. A null input to a two-argument formula makes the result undefined, not zero. |
| Zero denominators | Always undefined. Never zero, never infinity. `F-PCT-DELTA` from a zero baseline returns `None` with a warning rather than an infinite growth figure. |
| Rounding | Carried at full precision and applied once at the end. A test proves rounding once beats rounding per step: `[1.004, 1.004, 1.004]` sums to `3.01`, not `3.00`. |

**Non-finite values cannot propagate.** An infinite input means an earlier division already failed, so it is treated as undefined with a warning rather than carried forward into a confident-looking answer. This was found by a test and fixed during the phase.

**The config files are generated from the code.** `config/formulas.json` and `config/business_rules.json` are emitted from the registries rather than hand-written, and tests assert they have not drifted. The declared semantics therefore cannot disagree with the code that executes them.

### 5.5 PS → logic binding

`config/ps_logic_mapping.json` binds each of the 103 PSs to the formulas and rules its execution must use. Rules attach by predicate rather than by hand, so a new PS cannot forget one:

| Rule | Attaches when | PSs |
|---|---|---:|
| BR-001 persistency population | the PS reads Persistency | 22 |
| BR-002 minimum sample | the PS declares `small_sample_guard` | 19 |
| BR-006 personal data withheld | the PS reads Owner | 30 |
| BR-013 denominator declared | the PS spans more than one table | 54 |
| BR-014 no causal claim | the PS is diagnostic tier | 7 |

Two tests enforce the bindings that matter most: every PS touching Persistency is bound to BR-001, and every diagnostic PS is bound to BR-014.

### 5.6 Findings raised during the phase

One real defect was found and fixed: an infinite input was silently converted to `None` by the rounding helper, so a caller saw an undefined result with no explanation of why. `_num()` now rejects non-finite values explicitly and every affected formula emits a warning naming the cause. A non-numeric input such as a string is handled the same way — undefined with a warning, rather than raising.

### 6.4 Design decisions

**Seventeen patterns, not 103 executors.** Every PS executes through one of seventeen analytical patterns rather than through bespoke code. A pattern that had to be written for a single PS would be tested once; a pattern shared by twenty PSs gets tested hard. Each PS supplies a declarative plan naming its pattern and its inputs.

| Pattern | What it answers | PSs |
|---|---|---:|
| `group_metrics` | group, measure, rate, rank, compare against a baseline | 48 |
| `aggregate` | whole-population figures | 13 |
| `cohort_compare` | two cohorts profiled side by side | 7 |
| `concentration` | how much of a total sits in the largest groups | 6 |
| `distribution` | the shape of one numeric column | 6 |
| `timeseries` | a measure over chronological periods | 4 |
| `outliers` | interquartile fences within a peer group | 3 |
| `executive` | several sub-analyses, each keeping its own population | 4 |
| `driver_scan` | a leader versus a peer benchmark, attribute by attribute | 2 |
| `top_n` | the leading individual rows and their share | 2 |
| `scope_check` | a grounded refusal | 2 |
| `record_lookup`, `reconcile`, `quality_report`, `composite_score`, `two_stage_group`, `rule_breach` | one each | 6 |

**No pattern computes a number itself.** Every value goes through the formula engine, so each figure in an evidence package carries its formula id, its inputs and the semantics applied. Grouped aggregation runs in the query engine for speed, so each grouped statistic additionally records its whole-population equivalent through the formula engine — which both names the formula and gives the reader the portfolio figure the group values should be read against.

**Failure is a first-class outcome.** An execution that cannot answer returns an evidence package marked insufficient with the reason, never an empty result that reads like an answer. This covers a missing parameter, an out-of-range parameter, an unknown identifier, an empty population, and a group set entirely below the sample threshold.

**Parameters are validated against what the PS declares.** A plan substitutes only `$name` placeholders that resolve to declared, validated parameters, so a plan cannot reach for a value the PS never offered.

### 6.5 The evidence package

The package distinguishes four kinds of statement, because collapsing them is how an analysis turns an observation into a claim it cannot support:

| Kind | Source |
|---|---|
| observed | read directly from a CSV |
| calculated | produced by the formula engine, with its inputs recorded |
| compared | a difference against a declared baseline |
| unsupported | explicitly named as beyond what the data establishes |

Every package carries the tables and columns touched, the filters and join path, the population and its size, the calculations with their formula ids, the business rules applied with what each excluded, the comparison baseline, the ranking, sample sizes, data-quality notes, limitations, unsupported conclusions, and the full query provenance with row counts in and out of every step.

### 6.6 Findings raised during the phase

Five real defects were found by the tests and fixed:

- **A personal-data leak.** `_withhold_pii` applied BR-006 to get a frame with the columns dropped, then discarded that frame and filtered the original — so `Owner.Given.Name` and `Owner.Comm.Postal.Code` were still reaching record output. The query engine gained a recorded `drop_columns` operation and the helper now uses it.
- **Rule and derivation ordering.** Rules ran before derivations, so BR-005 could not filter on the duration it exists to guard. Derivations now come first.
- **A one-directional join.** Joining `policy_claims` from a claims base joined claims to itself, because the relationship was only ever traversed as declared. Relationships are now undirected: asking for the largest claims keeps the 134 claims as the population instead of expanding into 25,000 policies. The direction traversed is recorded in the audit trail.
- **A rate that was never computed.** PS-013 ranked products by `lapse_rate` but its plan never produced that column, so every rate came back null and the ranking was arbitrary. The catalogue build now refuses any plan that ranks, compares or trends on a column it does not compute — the check found exactly this one case.
- **Statistics with no formula behind them.** Six patterns reported figures the formula engine had never seen, so they carried no formula id and could not be audited. All now record their calculations.

One test expectation was wrong rather than the code: the client tiering returns 24,756 clients, not the 24,757 in Owner_Details, because the inner join drops the policy whose owner row carries the corrupted AppID (DQ-001) and that owner is the sole holder of their ClientID. The test now asserts the correct figure and states why.

### 7.5 The refusal paths

The reference implementation this project replaces answered *"How do smokers compare on premiums?"* by routing to an unrelated PS and returning a confident figure from a column that does not exist. Three independent guards prevent that here.

**1. Named-concept refusal, before any scoring.** A question resting on a field the datasets lack is refused and told which field is missing — 40 concepts mapped to the specific reason, from `smoker` ("no smoking or lifestyle field exists") to `by channel` ("CHANNEL is 'Banca' for every policy, so it cannot be compared"). Scoring such a question at all risks routing it.

**2. Invalid-identifier refusal.** An AppID, SALES_ID, branch number, product code or year that does not exist in the data is refused by name, however well the question otherwise matches.

**3. Confidence floor.** A question matching nothing well enough is refused rather than forced onto the nearest PS, and offered the three closest analyses instead.

A stated reason and a diagnostic "why" are deliberately separated. *"What reason did customers give for surrendering?"* is refused, because no reason was ever captured. *"Why are policies lapsing?"* routes to PS-040, which compares lapsed and in-force cohorts and states plainly that it reports association rather than cause.

### 7.6 Scoring design

Eight weighted signals, each bounded and reported with the decision so a match can be argued with:

| Signal | Weight | What it measures |
|---|---:|---|
| `example_similarity` | 0.16 | closeness to the PS's own example questions |
| `phrase_signal` | 0.18 | distinctive two-word phrases shared with the PS |
| `statement_similarity` | 0.07 | closeness to the PS statement |
| `concept_overlap` | 0.08 | declared concepts the question mentions |
| `domain_signal` | 0.07 | vocabulary tied to the PS's tables and columns |
| `dimension_signal` | 0.20 | what the question asks to be grouped by |
| `intent_signal` | 0.18 | the shape of answer requested |
| `tier_signal` | 0.05 | descriptive, analytical, diagnostic or executive |
| `entity_fit` | 0.01 | identifiers the question supplies |

Three design decisions did most of the work, each found by measurement rather than guessed:

- **Subject vocabulary and intent cues are kept apart.** An early version expanded superlatives like "top" and "best" into the matching vocabulary. That added identical tokens to every ranking question and let a handful of generic ranking PSs win regardless of subject — accuracy sat at 68%. Words describing the *shape* of an answer now feed only the intent signal.
- **Aliases are applied to both sides.** Expanding only the question inflated its term set and *lowered* overlap against the very PS it should match: PS-049, whose statement is word-for-word one of the test questions, was losing until the PS text was expanded the same way.
- **The grouping dimension is the sharpest discriminator.** "Which states write the most business" and "which are the highest-value policies" read almost identically on vocabulary and shape; what separates them is what the question asks to be grouped by. A dimension counts only in genuine grouping context ("which X", "by X", "per X"), and a PS is credited for what it *filters* on as well as what it groups by — without that, "how many policies have stopped paying" routed to the unfiltered total.

### Known limitations

- One question in 85 routes to a defensible but non-ideal PS: 'How many unit linked policies do we have?' reaches the per-product breakdown rather than the traditional-versus-ULIP split. Both answer the question; neither fabricates.
- The suite is 119 hand-written queries. It covers the nine specified categories but is not a substitute for real user phrasing, which will surface gaps this suite cannot.

### 8.4 Evidence tables

Six tables are produced from an evidence package, in reading order. Nothing is computed at this layer — every value already exists in the package, and presentation only decides what to show and how to label it.

| Table | Purpose |
|---|---|
| `result` | the analytical table itself, unaltered from the evidence |
| `aggregates` | whole-population figures, one metric per row |
| `records` | individual source rows, each keeping its `__row_id` |
| `calculations` | **the audit table** — every figure with its formula id, inputs and warnings |
| `business_rules` | which rules were applied and exactly what each excluded |
| `limitations` | what the analysis cannot establish, stated as its own table |

**Units are explicit, because that is where numbers quietly mislead.** A column is classified from its name and values as money, rate, count, days, identifier or text, and formatted accordingly under BR-011: money and rates to two decimals, counts as integers with no decimal point, ratios to four. A test asserts no count column can ever gain a decimal.

**Qualifications travel with the number they qualify.** The small-sample threshold and the count of excluded groups, the baseline a ranking is measured against, data-quality findings and every declared limitation all become footnotes on the table rather than being dropped in presentation.

### 8.5 Charts and how they are held to the evidence

A chart is the most persuasive thing this system produces and therefore the easiest place to mislead. Two rules hold it down, and the second is enforced by code rather than by care:

**1. A chart is emitted only when the evidence supports the shape asked for.** Insufficient evidence produces no chart. A scalar answer produces no chart — a single number cannot honestly become a bar. A PS that asked for a table gets a table.

**2. Every plotted value must already exist in the evidence.** Nothing is computed, interpolated, smoothed or extrapolated at this layer.

`verify_chart()` re-derives every category, series value, baseline and annotation from the evidence package and returns a list of discrepancies. The Phase 6 gate is that this list is empty for all 79 charts — and the tests additionally tamper with a value, a category, a series, a baseline and a problem id to confirm the check actually catches each one, rather than passing because it looks at nothing.

| Chart family | Types | Drawn from |
|---|---|---|
| Categorical | bar, horizontal bar, grouped bar, stacked bar, pie, donut, waterfall, heatmap | the grouped result table |
| Series | line, multi-line | chronologically ordered periods |
| Distribution | histogram, box | banded counts, annotated with the evidence median and mean |
| Point | scatter | two numeric columns of the result table |
| Tiles | KPI tiles | the aggregates, never a table |

Charts are capped at 25 categories and declare truncation when capped. A ranking chart plots the measure it was actually ranked by and carries its baseline as an annotation. A diagnostic chart carries the causation disclaimer into its footnotes; a time series carries the incomplete-final-period warning.

### 9.4 Architecture and the validation contract

```
evidence  ->  prompt  ->  model  ->  validate  ->  answer
                                        |
                                        +-- rejected -> deterministic answer
```

**The validator, not the prompt, is what makes the grounding claim true.** A prompt is a request; a validator is a guarantee. Every answer the model returns is checked against the evidence it claims to rest on, and an answer that fails is discarded before anyone reads it.

| Check | What it rejects |
|---|---|
| number fidelity | any figure not present in the evidence, including correctly *recomputed* ones — the model must not do arithmetic at all |
| entity fidelity | any product, agent or identifier the evidence does not name |
| causal safety | a causal claim where the evidence states cause cannot be established |
| concision | more than 7 sentences or 190 words |
| insufficient evidence | an answer that supplies figures when no analysis completed |
| leaked internals | mention of formula ids, tables or the prompt itself (warning, not rejection) |

Rounding is handled asymmetrically and deliberately: the **evidence** side expands to every legitimate spelling, so `10.948` may honestly be written `10.95` or `10.9`; the **answer** side is compared exactly as written. Expanding both sides was an early bug — a fabricated `99.9` rounded to `100` and matched a common linguistic number, so a made-up rate passed. A test caught it.

### 9.5 Fallback behaviour

**The deterministic composer is the fallback, and it is not a stub.** It writes the executive answer from the evidence package with no model involved, following the same answer contract the specification sets out: direct answer, then the finding, then the supporting number. Nine composers cover the nine answer shapes.

It can be this capable because the hard part was already finished. Every figure was computed, checked and labelled before any model was called, so losing the LLM costs fluency, not correctness:

> *"P91 leads on lapse rate at 26.07%. The portfolio lapse rate across all policies is 10.95%, so the gap is 15.13%. That is based on 4,721 policies. 1 group fell below the 50-row minimum sample and is excluded from ranking."*

Six conditions route to it, and each is tested: no model configured, SDK missing, credentials missing, API error or timeout, model refusal, and validation failure. The fallback's own output is validated too — nothing reaches a reader unchecked.

**No failure propagates.** A test drives five distinct exception types through the summarizer and asserts the user still receives an answer every time.

### 9.6 Model and provider choice

The specification says only "the connected LLM API" and names no provider. The integration targets **Groq** (`llama-3.3-70b-versatile`) through the official `groq` SDK for fast executive reasoning, with optional `anthropic` and deterministic fallback behind an interface that keeps the choice swappable.

| Setting | Value | Why |
|---|---|---|
| Provider | `groq` | ultra-low latency inference for executive answers |
| Model | `llama-3.3-70b-versatile` | fast, highly accurate summarization of evidence |
| `max_tokens` | 1024 | executive answers are short by contract |
| Timeout | 30s, 2 retries | a summarizer that hangs is worse than one that falls back |
| Fallback | `DeterministicClient` | full functionality with no external API calls |

The client is constructed lazily and never at import time, so a missing SDK or absent credentials is a runtime fallback rather than a broken application.

The suite runs with no API key set, because the deterministic path is a first-class implementation rather than a test double.

### 9.7 Findings raised during the phase

Three real defects, each found by a test:

- **The validator was too permissive.** Expanding the answer's figure by rounding let a fabricated `99.9` round to `100` and match a linguistic number. Expansion is now confined to the evidence side.
- **The composer truncated counts.** `int(322518.71)` printed `322,518`, a figure the evidence does not contain — the validator rejected the system's own fallback answer. Counts now round.
- **The hedging regex could not match its own prefixes.** A trailing `\b` after `observ` meant `observed` never matched, so every properly hedged diagnostic answer was rejected as an unhedged causal claim.

### Known limitations

- The causal-safety check is lexical. It catches the causal phrasings a summarizer actually produces, but a sufficiently indirect causal implication could pass.

### 10.5 How the layers are joined

```
question -> route -> execute -> evidence -> tables + chart -> summarize -> answer
```

Every layer beneath already refuses rather than guesses, and the chatbot's job is to carry those decisions through faithfully rather than paper over them. A question the router will not route never reaches an executor; an execution that cannot produce evidence never reaches the summarizer; an answer that fails validation never reaches the user.

Each outcome is distinct, so the interface can say which happened:

| Outcome | Meaning |
|---|---|
| `answered` | routed, executed, evidence produced, answer validated |
| `needs_clarification` | two analyses matched equally well; the options are offered |
| `refused` | the data cannot support the question, or the identifier does not exist |
| `could_not_complete` | routed and executed, but the evidence was insufficient |

A refusal carries no tables and no chart — a test asserts it, because presenting evidence beside a refusal implies an answer was found.

### 10.6 Conversation memory

**Conversation memory is deliberately shallow.** The specification asks for context "where safe and useful", and the qualifier is the important half:

- Only **entities** carry forward — product, state, agent, policy, status, bucket, branch. The analysis itself never does, because carrying it would let *"and for P22?"* silently re-run something the user has moved on from.
- Context applies only to a question that reads as elliptical: a short follow-up, or one opening with *"what about"*, *"and for"*, *"same for"*. A self-contained question is routed on its own terms, and a test asserts it.
- **Nothing carries forward from a refused turn.** A rejected premise must not leak into the next answer, so memory is read from the last *answered* turn only.
- When context is applied, the turn reports what was carried and the interface prints it, so a user is never silently answered about something they did not ask.

### 10.7 The interface

A terminal interface with no dependency beyond the standard library, which keeps it as testable as everything under it. One question:

```
$ python -m src.ui.cli "Which product has the highest lapse rate?"
```

renders the answer, then a text bar chart drawn only from the chart spec's own values, then the evidence table with its units and footnotes, then what the analysis cannot establish, then a provenance footer naming the analysis, its confidence, the answer's source and the elapsed time. `--detail` adds the calculation and business-rule tables; `--json` emits the whole turn; no argument opens a session with `:help`, `:detail`, `:reset` and `:quit`.

Formatting follows the units the evidence layer declared, so a rate prints with a percent sign and a count never grows a decimal point.

### Known limitations

- The interface is a terminal one. Streamlit and FastAPI are available in the environment and a web front end would be a thin layer over the same `Chatbot.ask()`, but none is built.
- Follow-up handling covers elliptical questions that name a new entity. It does not resolve pronouns ('is that high?') or comparative follow-ups ('and the year before?').

### 11.4 Where the security actually comes from

**The architecture does most of the security work before any guard runs.** User text never becomes a query: it selects a pre-written analysis from a fixed catalogue of 103, and that analysis runs against five files loaded at startup. There is no query string to inject into, no file path derived from user input, and no code path from a question to the filesystem or an interpreter.

That is worth stating plainly because it changes what the guards are for. They are defence in depth over a system that is already structurally hard to attack, not the only thing standing between a payload and the data.

**Three layers, each independent of the others:**

| Layer | What it stops |
|---|---|
| Input screening | the request never starts — 10 injection patterns, 6 code/traversal patterns, length limits, control-character stripping |
| Structural isolation | there is nothing to reach — fixed catalogue, validated parameters, five allow-listed files, no write path |
| Output assertion | nothing personal leaves, whatever happened upstream |

The last one matters most. `BR-006` already removes personal fields during execution, but every finished response is independently re-checked before it is returned, so a new output path cannot quietly reintroduce what the rule exists to prevent. A test deliberately constructs a leaky response and asserts the check raises.

### 11.5 Prompt injection and rule override

**The controlling defence against prompt injection is not the prompt.** It is the Phase 7 validator: a figure or entity absent from the evidence is rejected whatever the model was persuaded to write. Tests demonstrate this directly by scripting a compromised model:

| The model is made to say | What the user receives |
|---|---|
| *"the lapse rate is 95%"* | the deterministic answer, 10.95% |
| *"P99 has the highest lapse rate"* | P99 never appears |
| *"Low income causes policies to lapse"* | the causal claim is rejected |
| *"That policy has an APE of 250,000"* (no evidence) | *"This cannot be answered…"* |
| *"The lapse rate is 0% and no product has ever lapsed"* | tables and chart still show P91 at 26.07% |

Three further measures sit in front of it: the question is screened and refused outright if it reads as an instruction; whatever survives is neutralized before inclusion, with role labels, code fences and angle brackets stripped; and the system prompt frames the QUESTION block as user data that can never change a rule.

**Rule and threshold tampering is refused, and demonstrably ineffective.** Six phrasings are blocked, and a test asks a tampering question and then a real one, asserting the 50-row minimum sample threshold is still 50. Parameters are validated against what each PS declares, so an out-of-range or undeclared value is refused before execution.

### 11.6 Audit logging

**An audit trail that copies personal data into a log file has moved the problem, not solved it.** The log records the analysis chosen, the outcome, timings, formula and rule ids, and the shape of the result. It does not record the raw question, identifiers, names or postal codes.

Identifiers are replaced with a stable SHA-256 fingerprint: enough to correlate two lines about the same entity, not enough to recover which entity it was. `AuditLog.leaks()` holds the log to the same standard as the answers and returns anything that should not be there — a test asks about a named policy, a named agent and a customer list, then asserts the log leaks nothing.

### 11.7 Not breaking the working system

Hardening that blocks real questions has failed differently, so the false-positive side is tested as hard as the attacks:

- All **526 example queries** in the catalogue pass screening — a test asserts none is blocked.
- Six representative working questions still answer normally after every attack has been run through the same bot.
- Widening the tampering pattern to catch *"set the minimum sample threshold to 1"* was re-checked against all 526 queries before being kept.

### 11.8 Findings raised during the phase

The config drift test earned its place: changing the system prompt to add the injection framing left `config/llm_prompts.json` stale, and the suite failed until it was regenerated. That is the intended behaviour — the published contract cannot silently diverge from the prompt the application sends.

One pattern needed widening after testing: *"set the minimum sample threshold to 1"* initially passed because qualifying words sat between the verb and the noun. It was widened and re-checked against all 526 catalogue queries.

### Known limitations

- Injection detection is lexical and will not catch every phrasing. It is layered rather than relied upon: the evidence validator is what makes a successful injection change the prose rather than the facts.
- There is no authentication or authorisation layer. Every user of this PoC sees the same portfolio-level analysis; per-user data scoping would be a new requirement, not a hardening of this one.
- Rate limiting is not implemented. Question length and result size are capped, but nothing limits how many questions one caller may ask.

### 12.4 What the baseline records, and why it is generated

**A regression test needs something to regress against, and that baseline has to be produced by running the system.** A hand-written expectation is a second implementation of the same logic, and it is the one that will be wrong.

So `scripts/build_regression_baseline.py` runs the system and records what it produced. The file is committed, which makes regenerating it a reviewable act: the diff shows exactly which figures moved, and an unexplained movement is the finding.

| Recorded | Count | What is held fixed |
|---|---|---|
| Problem statements | 103 | every headline figure, population, result table, formula and rule |
| Tables | 5 | row counts, column order, dtype and null count of every column |
| Formulas | 18 | declared semantics and the value each worked example produces |
| Example queries | 526 | the analysis each one routes to, at 95.82% accuracy |

Each entry carries both a digest, which catches any change at all, and the figures in plain text, so a failure says *what* moved rather than that two hashes differ.

**The suite is asymmetric by design.** A figure that moves, a question that stops routing correctly, or a data-quality caveat that disappears is a failure. A new problem statement, or a question that *starts* routing correctly, is reported as a skip. The tests should stand in the way of the system getting quietly worse, not in the way of it getting better.

### 12.5 A performance defect the benchmarks found

**The benchmark suite found a real performance defect on its first run.**

Executing the whole catalogue took 37.5 seconds, and two analyses accounted for nearly half of it — PS-083 at 11.3 s and PS-082 at 6.1 s, against a 364 ms mean. That distribution is the signature of an algorithm problem rather than a large-data problem.

The cause was in `Query.group_by`: it iterated the groups in Python and called the aggregator on each chunk. That reads well, but it costs one pandas call per group per measure — on a 25,000-customer grouping with six measures, 150,000 calls, each paying pandas' per-call overhead rather than doing meaningful work.

pandas can do the same work in one pass per measure. The aggregator table stays the source of truth for semantics; the vectorised path reproduces each aggregator's contract exactly — `sum` returning 0.0 for an all-null group, `mean` returning None, `std` requiring two observations.

| | Before | After | |
|---|---|---|---|
| PS-083 | 11,266 ms | 401 ms | 28x |
| PS-082 | 6,139 ms | 75 ms | 82x |
| PS-024 | 2,907 ms | 221 ms | 13x |
| Whole catalogue | 37.5 s | 10.6 s | 3.5x |
| Full test suite | 112 s | 81 s | despite 113 more tests |

### 12.6 The regression suite catching the one real change

**The regression suite then did the job it was built for.** Re-running it against the pre-optimisation baseline surfaced exactly one difference, in PS-073, and held every other figure in the catalogue fixed.

The investigation is worth recording because the first reading was wrong. A positional diff showed changes of up to 11.6 — alarming, until it turned out the row *order* had changed, so the comparison was reading different agents. Keyed by agent id, the picture was:

- **Raw sums** differed by at most 4.3e-14. pandas' vectorised sum uses pairwise summation, which is *more* accurate than the naive per-group sum: `86.80000000000003` became `86.8`.
- **Percentile ranks** moved by up to 1.65 points, because values that should have been exactly equal were previously separated by 1e-16. Ties that are real ties are now recognised as ties.
- **Ranks**: 10 of 50 agents moved, and every move was a swap within an adjacent pair — 27↔28, 35↔36, 37↔38, 41↔42, 47↔48 — five pairs that had been separated only by floating-point noise.

The new results are more correct, not less. The baseline was regenerated deliberately, after confirming the output is identical across repeated runs.

### 12.7 Caching, and why correctness is the hard part

**A cache is the one performance optimisation in this system that can produce a wrong answer** — and a particularly bad kind, since stale figures arrive with a formula id, a population size and full provenance, and read exactly like a fresh computation. Everything downstream would confirm a stale number as grounded, because against the cached evidence it *is* grounded.

Three properties make it safe:

| Property | How |
|---|---|
| Determinism | No analytical code reads the wall clock or any state outside the loaded frames — verified by grep, not assumed |
| Fingerprint | The key includes a content hash of the loaded frames plus catalogue, contract and executor versions. Removing one row or changing one cell invalidates every entry |
| Isolation | Entries are deep-copied in and out, so a caller that annotates a package — and the summarizer does — cannot change what the next caller receives |

A hit is disclosed rather than hidden: `provenance["cache"]` records that the figures were computed earlier and when, and the evidence keeps the timestamp of the computation that actually happened. Insufficient results are not cached, and `execute_fresh()` bypasses the cache entirely for the tests that must observe the computation itself.

Measured: **0.19 ms** against **19.3 ms** to recompute, roughly 100x.

### Known limitations

- PS-073's ranking contains adjacent pairs separated only by rounding. Their order is deterministic but arbitrary; a tie-breaking rule would be more honest than relying on group order.
